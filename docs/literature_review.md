# Literature review

> Revision of 22.10.2026. Bibliographic data were checked against publisher pages and conference records. The content is summarised from the abstracts and the result sections; the papers will be read in full while chapter 1 is written.

The review covers LLM-based approaches to Text-to-SQL, work on ambiguous questions, and the threats that appear when a system executes SQL generated by a model. For each source the table states what the project takes from it and which limitation it accounts for.

## 2. Analysis

### 2.1 LLM-based approaches to Text-to-SQL

Early measurements [4] showed that a large model without fine-tuning solves a considerable part of Spider [1] if the schema is presented well in the prompt. Later work improved three things.

DIN-SQL [5], MAC-SQL [7] and CHESS [8] make the selection of the required tables and values a separate step before generation. The larger the schema, the more this step matters: on BIRD [2], and especially on Spider 2.0 [3], the whole schema does not fit into the prompt or confuses the model. DAIL-SQL [6] showed that the largest accuracy gain comes from selecting "question → SQL" examples similar to the current question. DIN-SQL corrects the SQL with the same model, and MAC-SQL corrects it from an execution error. Self-Refine [15] shows the limit of self-criticism: a model often does not notice its own mistake.

From these works the project takes schema linking over a hybrid index (dense + BM25, fused with RRF [16]) with a search over values, as in CHESS, and dynamic examples, as in DAIL-SQL. The project has self-correction, but the error is found by a deterministic validator, which gives the model the exact reason and a hint.

In stage 1 of the evaluation self-correction hardly helped, because the agent's errors were semantic. This agrees with the limitation of MAC-SQL and Self-Refine: repair driven by formal errors misses queries that run without errors but answer a different question.

### 2.2 Ambiguity

Benchmarks [1–3] assume that a question has one correct answer. AmbiQT [10] and AMBROSIA [11] showed that for an ambiguous question models almost always choose one interpretation and do not say so. Both sets test whether a system can list the interpretations. A clarification dialogue appears in PRACTIQ [12], where the system asks back and the user answers.

Clarification with answer options has already been proposed in several systems. Sphinteract [18] distinguishes four types of ambiguity (column, output format, question interpretation, condition values), asks short questions with options and a free answer, and rebuilds the SQL after the answer. CLEAR [19] and AmbiSQL [20] have a similar structure: detect the ambiguity, offer options, rewrite the question; AmbiSQL also gives a taxonomy by database elements and by model reasoning. In the evaluation of Sphinteract the user was mostly replaced by a GPT-4o simulator working from the reference SQL, as in BIRD-Interact [23], where the simulated user is part of the benchmark itself.

CLARITY [21] shows that detection is not the hard part: models notice that there is an ambiguity but point poorly to the part of the schema where it lies. Two requirements follow: tie the clarification options to specific columns, and measure the correctness and completeness of the options separately from detection. Questions that cannot be answered from the given database are a separate case. MMSQL [22] distinguishes answerable, ambiguous, unanswerable and improper questions, and TrustSQL [24] evaluates abstention with a penalty metric. For this reason "the database does not contain the required data" is a separate route in the project: it is neither a clarification nor an off-topic question.

For Russian there is PAUQ [17], a Russian version of Spider for testing SQL generation. Among the works found there is no ready Russian dataset with ambiguous questions and clarification (search in arXiv, the ACL Anthology and open sources as of 22.10.2026).

The idea of clarification has already been described in [12, 18–20], so the contribution of the project lies in the combination of decisions. Clarification is built into a working read-only system and works together with five-level SQL validation: the options are tied to schema columns, and the graph pauses and resumes after the answer. The questions of the dataset are written in Russian, the difference between the results of the interpretations is checked automatically, as the AMBROSIA method requires, and the effect is measured by a paired comparison on the same questions with and without clarification.

A simulated user answers the clarifications, as in [12, 18, 23]. Real users behave differently, so the plan includes user testing.

### 2.3 Security

When a system executes SQL generated from the user's text, a class of P2SQL vulnerabilities appears [13]. Instructions can also come from the data that the model reads [14]. OWASP [25] lists both threats, together with excessive agency of the model, among the main risks of LLM applications.

The protection in the project therefore does not depend on the behaviour of the model. The DBMS role has read privileges only, the query runs in a read-only transaction with limits, the SQL is checked on the AST against a list of allowed constructs, and the data in the prompt is separated from the instructions. The input classifier is added as one more line of defence.

In stage 1 one of six indirect injections got into the explanation text, although the data was not affected. This agrees with the conclusion of [14]: the text the model writes must be checked separately.

## 3. Conclusions for the project

1. Selection of the schema and values is necessary, and its completeness (schema recall) should be measured separately.
2. The critic must be external and deterministic, but it catches only formal errors. Clarification, examples and error analysis help with semantic errors.
3. Ambiguous questions are common, and a stronger model alone does not solve them. Ambiguity has to be detected and clarified explicitly and measured on a set where the interpretations give different answers. Detecting it is not enough: its source in the schema must also be identified [21].
4. Execution safety comes from DBMS privileges and AST checks. A prompt gives no guarantees here.
5. Execution accuracy does not measure the usefulness of an answer: an "extra" explanatory column counts as an error. For this reason relaxed EX and manual error analysis were added to the evaluation [9].
6. "The database does not contain the required data", an ambiguous question and an off-topic question are different cases with different system reactions: a refusal with an explanation, a clarification, a rejection [22, 24].
