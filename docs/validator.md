# Multi-level SQL validation

The [`backend/app/validator`](../backend/app/validator) module decides whether SQL generated by the LLM may reach the database. The checks are done **in code**: the system prompt only describes the rules, and the guarantee comes from a deterministic validator and from the DBMS privileges.

```text
SQL from the LLM
  │
  ├─ 1. Syntax             sqlglot: parse, exactly one statement             ─┐
  ├─ 2. Policy             AST: SELECT only, no dangerous nodes/functions    │ no database, < 3 ms
  ├─ 3. Schema             tables, columns, unambiguity, date literals       ─┘
  │      ↓ normalisation: comments removed, outer LIMIT ≤ max_rows + 1
  ├─ 4. Plan               EXPLAIN (without ANALYZE): cost, Cartesian product
  └─ 5. Execution          READ ONLY transaction, timeout, row and byte limits
         ↓
     QueryResult
```

Interface (CONTRACTS §3):

```python
report = validate(sql, snapshot, limits)          # levels 1–3, stops at the first failure
level4 = await explain(report.normalized_sql, conn, limits)
result = await execute_readonly(report.normalized_sql, conn, limits)   # ExecutionError on failure
```

Each level returns a `ValidationLevelResult` with the fields `passed`, `message` (for the user), `hint` (for self-correction) and `fatal`. With `fatal=True` self-correction is forbidden: the agent does not try to "repair" an attempt to change data and refuses instead.

## Level 1. Syntax

| Rule | Reason |
|---|---|
| The query is parsed by `sqlglot` (`postgres` dialect) | An error with the line and position is a precise hint for self-correction |
| **Exactly one** statement, otherwise `fatal` | `SELECT 1; DROP TABLE orders` is the classic way to hide a dangerous command after a harmless one |
| `SELECT` without columns is rejected | sqlglot parses a bare `SELECT` without an error |
| Anything sqlglot cannot parse is rejected | Only what has passed all levels is executed. If the parser does not understand a construct, it is not executed (allowlist principle) |

## Level 2. Read-only policy (a violation is always fatal)

The check works on the **parse tree**, not on the query text. Letter case (`DeLeTe`), quotes (`"pg_sleep"(10)`), line breaks and comments therefore do not help to bypass the rules. The whole tree is traversed, including subqueries and CTEs.

| Rule | What it blocks | Reason |
|---|---|---|
| The root is only `SELECT`, `UNION`, `INTERSECT`, `EXCEPT` | DDL, DML, utility commands | sqlglot parses `LISTEN ch` and `TABLE orders` as an expression with an alias, so the root is checked explicitly |
| Forbidden nodes anywhere in the tree | `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `DROP`, `CREATE`, `ALTER`, `TRUNCATE`, `COPY`, `GRANT`, `REVOKE`, `SET`, transactions, `VACUUM`/`DO`/`CALL`/`PREPARE`/`SHOW` (the `Command` node) | In PostgreSQL a CTE can modify data: `WITH d AS (DELETE … RETURNING *) SELECT …` looks like a `SELECT` |
| `SELECT … INTO` | Creating a table from a query | A write disguised as a read |
| `FOR UPDATE` / `FOR SHARE` | Row locking | Blocks the application and requires the `UPDATE` privilege |
| Functions by name prefix | `pg_sleep*`, reading and writing server files (`pg_read_file`, `pg_ls_*`, `lo_*`), `dblink*`, session control (`pg_terminate_backend`, `set_config`, `current_setting`), `query_to_xml` (runs SQL from a string), `nextval`/`setval`, `txid_*`, advisory locks, `pg_notify`, replication and WAL | Side effects, leaks of server data, bypassing the timeout or running arbitrary SQL inside a "harmless" SELECT |
| System catalogs | `pg_catalog.*`, `information_schema.*`, unqualified `pg_*` (`pg_user`, `pg_shadow`, `pg_stat_activity`) | Passwords, active sessions, the structure of other schemas; the agent needs only the schema from the snapshot |

## Level 3. Schema check

| Rule | Hint for self-correction |
|---|---|
| The table exists (taking `search_path` into account: first `public`, then the only schema with that name) | Similar names (`order` → `orders`) or the list of available tables |
| The column exists (`sqlglot.optimizer.qualify`) | Similar columns of the query's tables + columns with the same name in other tables: `o.paid_at` → "`orders.created_at`, `payments.paid_at`" |
| The column reference is unambiguous | "Column `id` exists in `orders.id`, `customers.id`; specify the table" |
| A string compared with a date is a date | "`'last quarter'` is compared with a date" → example `date_trunc('quarter', now())`. ISO dates and special PostgreSQL values (`now`, `today`, `yesterday`, `epoch`, …) are allowed |

Before the check, unquoted identifiers are lowercased, as PostgreSQL does: `SELECT STATUS FROM ORDERS` is correct. CTEs and table functions (`generate_series`) are not counted as tables.

**Normalisation.** After level 3 the comments are removed (they may contain prompt injection text), and the outer `LIMIT` is capped at `max_rows + 1`. If the user set a smaller `LIMIT`, it is kept. If it is larger, the query is wrapped: `SELECT * FROM (…) AS limited LIMIT 1001`. The extra row signals that the result was truncated.

## Level 4. Execution plan

`EXPLAIN (FORMAT JSON)` **without `ANALYZE`**: with `ANALYZE` the query would be executed. It runs in a read-only transaction with a timeout.

| Rule | Threshold | Hint |
|---|---|---|
| Cartesian product: a `Nested Loop` without a `Join Filter`, an inner side without an index condition, both sides > 10,000 rows | `cartesian_min_rows` | "Check the JOIN … ON conditions" |
| Cost estimate | `SQL_MAX_EXPLAIN_COST` (1,000,000) | "Add filters or aggregation" |
| Planner error (incompatible types and similar) | — | The PostgreSQL error text |

There is no separate threshold on the number of rows in the plan: the result is already limited by `LIMIT`, and large intermediate results are reflected in the cost.

## Level 5. Execution

| Measure | Value |
|---|---|
| Connection role | `SELECT` only. Checked when the source is registered (ADR-008) |
| Transaction | `BEGIN READ ONLY … ROLLBACK` |
| Timeouts | `SET LOCAL statement_timeout` and `idle_in_transaction_session_timeout` (`SQL_STATEMENT_TIMEOUT_MS`) |
| Number of rows | The cursor reads at most `max_rows + 1` rows |
| Response size | 2 MB of JSON, then `truncated = true` |
| Types | `numeric` → number, dates → ISO string, `bytea` → `<binary N bytes>` |

Even if levels 1–4 let a modifying query through, the `READ ONLY` transaction will not execute it. A test calls `execute_readonly("DELETE FROM orders")` as a **superuser** and checks that the data has not changed.

## Results

The datasets are in [`evals/datasets/unsafe/`](../evals/datasets/unsafe/) and are shared by the tests and the role 7 experiments.

**88 attacks, 100% blocked**; none reached level 3:

| Category | Total | Level 1 | Level 2 |
|---|---|---|---|
| DDL | 15 | 0 | 15 |
| DML | 8 | 0 | 8 |
| Several statements | 4 | 4 | 0 |
| Data-modifying CTEs | 6 | 0 | 6 |
| `SELECT INTO` and locks | 6 | 0 | 6 |
| Session and utility commands | 19 | 2 | 17 |
| Dangerous functions | 16 | 0 | 16 |
| System catalogs | 6 | 0 | 6 |
| Obfuscation (case, quotes, comments, whitespace) | 8 | 2 | 6 |
| **Total** | **88** | **8** | **80** |

87 of 88 have `fatal = true`. The exception is `NOTIFY channel, 'x'`: sqlglot does not parse it, so it is rejected as a syntax error and is not executed either.

**42 harmless queries, 0 false blocks.** They include window functions, CTEs, `UNION`/`INTERSECT`/`EXCEPT`, `LATERAL`, `FILTER`, `generate_series`, the string literal `'DROP TABLE orders'`, the aliases `deleted` and `update_count`, and queries in upper case. All 42 pass levels 1–5 on the real demo database as the `s2d_reader` role.

**Property-based tests** (hypothesis, 300 examples): modifying subqueries in CTEs and dangerous expressions anywhere in an allowed query (`SELECT`, `WHERE`, `HAVING`, `UNION`, subquery), with different letter case and comments, are always blocked.

**Speed:** levels 1–3 on harmless queries take 0.58 ms at the median, 1.46 ms at p95 and 2.9 ms at most (requirement: < 20 ms).

**Test coverage:** 96% of the lines and branches of the `app/validator` module.

## Limitations

- The policy is designed for **PostgreSQL**. Other dialects would need their own lists of functions and system catalogs.
- The list of dangerous functions is a denylist: a new dangerous function from an extension may be missing from it. Level 5 protects against this: a role without write privileges, a read-only transaction and a timeout.
- The `EXPLAIN` cost estimate depends on up-to-date statistics (`ANALYZE`) in the target database.
- The date literal check covers only a direct comparison of a column with a string. Expressions such as `created_at::text = '…'` are not analysed.
