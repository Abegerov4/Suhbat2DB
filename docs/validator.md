# Многоуровневая проверка SQL

Модуль [`backend/app/validator`](../backend/app/validator) решает, может ли SQL, сгенерированный LLM, дойти до базы данных. Проверку выполняет **код, а не промпт**: system prompt только описывает правила, а гарантию даёт детерминированный валидатор и права СУБД.

```text
SQL от LLM
  │
  ├─ 1. Синтаксис          sqlglot: разбор, ровно одно выражение          ─┐
  ├─ 2. Политика           AST: только SELECT, без опасных узлов/функций   │ без БД, < 3 мс
  ├─ 3. Схема              таблицы, столбцы, однозначность, литералы дат  ─┘
  │      ↓ нормализация: комментарии удалены, внешний LIMIT ≤ max_rows + 1
  ├─ 4. План               EXPLAIN (без ANALYZE): стоимость, декартово произведение
  └─ 5. Выполнение         READ ONLY-транзакция, тайм-аут, лимит строк и байтов
         ↓
     QueryResult
```

Интерфейс (CONTRACTS §3):

```python
report = validate(sql, snapshot, limits)          # уровни 1–3, останавливается на первом провале
level4 = await explain(report.normalized_sql, conn, limits)
result = await execute_readonly(report.normalized_sql, conn, limits)   # ExecutionError при ошибке
```

Каждый уровень возвращает `ValidationLevelResult` с полями `passed`, `message` (для пользователя), `hint` (для самокоррекции) и `fatal`. При `fatal=True` самокоррекция запрещена: агент не пытается «починить» попытку изменить данные, а отказывает.

## Уровень 1. Синтаксис

| Правило | Почему |
|---|---|
| Запрос разбирается `sqlglot` (диалект `postgres`) | Ошибка с номером строки и позиции — точная подсказка для самокоррекции |
| **Ровно одно** выражение, иначе `fatal` | `SELECT 1; DROP TABLE orders` — классический способ спрятать опасную команду после безобидной |
| `SELECT` без столбцов отклоняется | sqlglot разбирает голый `SELECT` без ошибки |
| Всё, что sqlglot не разобрал, отклоняется | Выполняется только то, что прошло все уровни. Если парсер не понимает конструкцию, она не исполняется (принцип allowlist) |

## Уровень 2. Политика «только чтение» (нарушение всегда фатально)

Проверка идёт по **дереву разбора**, а не по тексту запроса. Поэтому регистр (`DeLeTe`), кавычки (`"pg_sleep"(10)`), переносы строк и комментарии не помогают обойти правила. Обходится всё дерево, включая подзапросы и CTE.

| Правило | Что блокирует | Почему |
|---|---|---|
| Корень — только `SELECT`, `UNION`, `INTERSECT`, `EXCEPT` | DDL, DML, служебные команды | sqlglot разбирает `LISTEN ch` и `TABLE orders` как выражение с псевдонимом, поэтому корень проверяется явно |
| Запрещённые узлы в любом месте дерева | `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `DROP`, `CREATE`, `ALTER`, `TRUNCATE`, `COPY`, `GRANT`, `REVOKE`, `SET`, транзакции, `VACUUM`/`DO`/`CALL`/`PREPARE`/`SHOW` (узел `Command`) | В PostgreSQL CTE может изменять данные: `WITH d AS (DELETE … RETURNING *) SELECT …` выглядит как `SELECT` |
| `SELECT … INTO` | Создание таблицы из выборки | Запись под видом чтения |
| `FOR UPDATE` / `FOR SHARE` | Блокировка строк | Блокирует работу приложения, требует права `UPDATE` |
| Функции по префиксу имени | `pg_sleep*`, чтение и запись файлов сервера (`pg_read_file`, `pg_ls_*`, `lo_*`), `dblink*`, управление сессиями (`pg_terminate_backend`, `set_config`, `current_setting`), `query_to_xml` (выполнение SQL из строки), `nextval`/`setval`, `txid_*`, advisory-блокировки, `pg_notify`, репликация и WAL | Побочные эффекты, утечка данных сервера, обход тайм-аута или выполнение произвольного SQL внутри «безобидного» SELECT |
| Системные каталоги | `pg_catalog.*`, `information_schema.*`, неквалифицированные `pg_*` (`pg_user`, `pg_shadow`, `pg_stat_activity`) | Пароли, активные сессии, структура других схем — агенту нужна только схема из снимка |

## Уровень 3. Сверка со схемой

| Правило | Подсказка для самокоррекции |
|---|---|
| Таблица существует (с учётом `search_path`: сначала `public`, затем единственная схема с таким именем) | Похожие имена (`order` → `orders`) или список доступных таблиц |
| Столбец существует (`sqlglot.optimizer.qualify`) | Похожие столбцы таблиц запроса + столбцы с тем же именем в других таблицах: `o.paid_at` → «`orders.created_at`, `payments.paid_at`» |
| Ссылка на столбец однозначна | «Столбец `id` есть в `orders.id`, `customers.id` — укажите таблицу» |
| Строка, сравниваемая с датой, — дата | «`'прошлый квартал'` сравнивается с датой» → пример `date_trunc('quarter', now())`. Допускаются ISO-даты и особые значения PostgreSQL (`now`, `today`, `yesterday`, `epoch`, …) |

Перед проверкой идентификаторы без кавычек приводятся к нижнему регистру, как это делает PostgreSQL: `SELECT STATUS FROM ORDERS` корректен. CTE и табличные функции (`generate_series`) таблицами не считаются.

**Нормализация.** После уровня 3 комментарии удаляются (в них может быть текст prompt injection), а внешний `LIMIT` ограничивается значением `max_rows + 1`. Если пользователь сам поставил меньший `LIMIT`, он сохраняется. Если больше, запрос оборачивается: `SELECT * FROM (…) AS limited LIMIT 1001`. Лишняя строка служит признаком того, что результат усечён.

## Уровень 4. План выполнения

`EXPLAIN (FORMAT JSON)` **без `ANALYZE`**: с `ANALYZE` запрос был бы выполнен. Выполняется в read-only транзакции с тайм-аутом.

| Правило | Порог | Подсказка |
|---|---|---|
| Декартово произведение: `Nested Loop` без `Join Filter`, внутренняя сторона без условия по индексу, обе стороны > 10 000 строк | `cartesian_min_rows` | «Проверьте условия JOIN … ON» |
| Оценка стоимости | `SQL_MAX_EXPLAIN_COST` (1 000 000) | «Добавьте фильтры или агрегацию» |
| Ошибка планировщика (несовместимые типы и т.п.) | — | Текст ошибки PostgreSQL |

Отдельный порог на число строк в плане не используется: результат и так ограничен `LIMIT`, а большие промежуточные выборки отражаются в стоимости.

## Уровень 5. Выполнение

| Мера | Значение |
|---|---|
| Роль подключения | Только `SELECT`. Проверяется при регистрации источника (ADR-008) |
| Транзакция | `BEGIN READ ONLY … ROLLBACK` |
| Тайм-ауты | `SET LOCAL statement_timeout` и `idle_in_transaction_session_timeout` (`SQL_STATEMENT_TIMEOUT_MS`) |
| Число строк | Курсор читает не больше `max_rows + 1` строк |
| Размер ответа | 2 МБ JSON, затем `truncated = true` |
| Типы | `numeric` → число, даты → ISO-строка, `bytea` → `<binary N bytes>` |

Даже если уровни 1–4 пропустят изменяющий запрос, `READ ONLY`-транзакция его не выполнит. Тест вызывает `execute_readonly("DELETE FROM orders")` под **суперпользователем** и проверяет, что данные не изменились.

87 из 88 — с `fatal = true`. Исключение — `NOTIFY channel, 'x'`: sqlglot его не разбирает, поэтому он отклоняется как синтаксическая ошибка и тоже не выполняется.

**42 безобидных запроса — 0 ложных блокировок.** Среди них оконные функции, CTE, `UNION`/`INTERSECT`/`EXCEPT`, `LATERAL`, `FILTER`, `generate_series`, строковый литерал `'DROP TABLE orders'`, псевдонимы `deleted` и `update_count`, запросы в верхнем регистре. Все 42 проходят уровни 1–5 на настоящей демо-БД под ролью `s2d_reader`.

**Property-based тесты** (hypothesis, 300 примеров): изменяющие подзапросы в CTE и опасные выражения в любом месте допустимого запроса (`SELECT`, `WHERE`, `HAVING`, `UNION`, подзапрос) с разным регистром и комментариями всегда блокируются.

**Скорость:** уровни 1–3 на безобидных запросах — медиана 0,58 мс, p95 — 1,46 мс, максимум 2,9 мс (требование: < 20 мс).

**Покрытие тестами:** 96% строк и ветвей модуля `app/validator`.

## Ограничения

- Политика рассчитана на **PostgreSQL**. Другие диалекты потребуют своих списков функций и системных каталогов.
- Список опасных функций — denylist: новая опасная функция из расширения может в него не попасть. Защиту от этого обеспечивает уровень 5: роль без прав на запись, read-only транзакция и тайм-аут.
- Оценка стоимости `EXPLAIN` зависит от актуальности статистики (`ANALYZE`) в целевой БД.
- Проверка литералов дат покрывает только прямое сравнение столбца со строкой. Выражения вроде `created_at::text = '…'` не анализируются.
