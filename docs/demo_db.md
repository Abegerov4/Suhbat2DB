# Suhbat2DB demo database

A synthetic database of a retail chain selling electronics and household goods in Kazakhstan. It is used for development, for the demonstration at the defence and for the set of ambiguous questions `ambiguous_ru` (role 7).

The data is **synthetic**: it is generated by [`demo_db/seed.py`](../demo_db/seed.py) with a fixed seed. Conclusions about the agent's quality on this database are complemented by the evaluation on Spider and BIRD.

## Running

```bash
make up-lite              # target-db must be running
make seed                 # full volume, ~8 seconds
make seed SCALE=0.05      # 5% of the volume (used in CI)
make test-demo-db         # 68 tests: role privileges, integrity, presence of the "traps"
```

Running `make seed` again recreates the `public` schema. The data is deterministic: two runs give byte-identical tables.

**Connection:** `localhost:5443`, database `demo`. The administrator is `TARGET_DB_ADMIN_USER`, the agent is `s2d_reader` (passwords in `.env`).

## Volume (SCALE=1.0)

| Table | Rows | Contents |
|---|---|---|
| `regions` | 12 | 3 cities of republican significance + 9 regions |
| `cities` | 16 | Cities weighted by population |
| `customers` | 30,000 | 10% organisations (b2b); 22% registered but never bought anything |
| `managers` | 56 | Store managers; some were dismissed and some hired during the period |
| `categories` / `products` | 10 / 200 | 8% of the products are discontinued |
| `orders` | 100,000 | 01.10.2023 – 18.10.2026, growth of ~25% per year, seasonality |
| `order_items` | ~186,000 | Price at the time of sale (inflation of ~10% per year) |
| `payments` | ~96,000 | Some b2b orders are paid with two payments |
| `returns` | ~4,600 | ~5% of the delivered orders |
| `fiscal_calendar` | 1,826 | 2023–2027, fiscal year starting on 1 April |

The database time zone is `Asia/Almaty`, so `date_trunc('quarter', created_at)` counts quarters in local time.

## Traps: sources of ambiguity

Each trap is a property of the data that makes one question admit several correct SQL queries with **different answers**. A test checks the presence of each trap ([`test_data.py`](../demo_db/tests/test_data.py)). The figures below are computed on the full volume.

### 1. "Sales": which measure (metric)

*"Show sales for last quarter"* (July–September 2026):

| Interpretation | SQL basis | Answer |
|---|---|---|
| Revenue by order date | `sum(orders.total_amount)`, without `cancelled` | 5,612.2 million ₸ |
| Revenue by payment date | `sum(payments.amount)` by `paid_at` | 5,456.5 million ₸ |
| Revenue minus returns | `total_amount − returns.amount` | 5,412.5 million ₸ |
| Number of orders without cancelled ones | `count(*)`, `status <> 'cancelled'` | 8,471 |
| Number of all orders | `count(*)` | 8,998 |
| Units sold | `sum(order_items.quantity)` | 46,263 |
| ❌ Error: `JOIN orders × payments` | sum of `total_amount` after the JOIN | 6,712.1 million ₸ (+20%) |

The last row shows a typical generation error, not an interpretation: a b2b order can have several payments, so the JOIN duplicates the order rows.

### 2. "Quarter" and "year": calendar or fiscal (temporal)

The fiscal year starts on 1 April (`FY2026` = 01.04.2026–31.03.2027).

*"Revenue for the first quarter of 2026"*:

| Interpretation | Period | Answer |
|---|---|---|
| Calendar Q1 2026 | January–March 2026 | 4,421.1 million ₸ |
| Fiscal FQ1 FY2026 | April–June 2026 | 5,054.3 million ₸ |

The same applies to "for 2025": calendar 2025 or `FY2025` (April 2025 – March 2026).

One more temporal trap is **order date or payment date**. Cash-on-delivery payments and b2b transfers arrive 1–10 days later, so 1,655 payments fall into a different quarter than the order itself.

### 3. "Almaty": city or region (value)

*"Revenue in Almaty for 2025"*:

| Interpretation | Condition | Answer |
|---|---|---|
| City of republican significance | `regions.name = 'Алматы'` | 5,433.6 million ₸ |
| City and Almaty region | `regions.name ILIKE 'алмат%'` | 6,517.3 million ₸ |

### 4. "Customers": whom to count (scope)

| Interpretation | Condition |
|---|---|
| All registered | the whole `customers` table (30,000) |
| Bought at least once | `EXISTS (SELECT 1 FROM orders …)` |
| Active | `is_active` (an order in the last 12 months) |
| Individuals only / organisations only | `segment = 'b2c' / 'b2b'` |

### 5. "Best managers": by which criterion (scope)

*"Who is the best manager for 2025?"* By revenue it is **Vasilyev Venedikt Vitalyevich**, by number of orders it is **Abenova Tomiris**. It is also unclear whether dismissed managers should be counted (`fired_at IS NOT NULL`). Online orders (39%) have no manager: `JOIN managers` silently drops them.

### 6. "Price": current or at the time of sale (schema)

`products.price` is the current price, and `order_items.unit_price` is the price at the time of sale. Because of inflation they differ in almost every row. *"Average price of smartphones sold"* gives different answers depending on the chosen column.

### 7. Cancelled orders and statuses

6% of the orders are cancelled. The question *"how many orders in September"* may include them or not. Recent orders can have the statuses `new`, `paid`, `shipped`: not all of them have been delivered yet.

## Tests

| File | What it checks |
|---|---|
| [`test_reader_role.py`](../demo_db/tests/test_reader_role.py) | 17 dangerous commands × 2 modes (read-only session and a session with read-only turned off): DDL, DML, `SELECT INTO`, `FOR UPDATE`, data-modifying CTE, `COPY TO` a file, reading server files. Also: `GRANT` has no effect, `pg_sleep(10)` is interrupted by the 5-second timeout, the role has no superuser attributes, `PUBLIC` has no privileges on the database |
| [`test_data.py`](../demo_db/tests/test_data.py) | 11 integrity invariants (order total = items − discount, payments = order total, the manager was employed on the order date and in the customer's region, …), comments on all tables and columns, the fiscal calendar, presence of all traps, seasonality |

## Why privileges are checked in two modes

`ALTER ROLE s2d_reader SET default_transaction_read_only = on` only sets the **default** value: any session can run `SET TRANSACTION READ WRITE`. The real guarantee is therefore the **absence of privileges** (`INSERT`, `UPDATE`, `DELETE`, `CREATE`, `TEMP`), and the read-only mode is only an additional layer. The second set of tests turns read-only off and checks that writing is still forbidden by the privileges.
